Case 1 · Human-in-the-loop

An approval gate between the agent and every write

In plain terms: the AI can only change company data when that company's settings allow it, and a person can approve each change before it happens.

Outcome: All 31 write tools go through one checkpoint, and a CI test fails if a new write tool is not classified. Public version: 95 tests.

Problem
An agent runs at 3 a.m. with nobody watching. If the model calls a delete tool, it happens on real data. Each organisation needs a per-action choice: do it, ask me first, or never. It has to hold even when the model is tricked.
My role
Designed and built it, and shipped it in five phases. The model proposes, code decides.
Stack
Python, LangChain and LangGraph tools, PostgreSQL, CloudEvents. Public version: SQLite.
How it works
Show the details
  • A fixed map ties each write tool to one permission action. Unmapped tools are refused before any lookup, and delete tools are denied on purpose.
  • The mode (Autonomous, Suggest Only, Disabled) is read fresh on every call. Suggest Only stores a draft with signed arguments, and approval replays exactly those arguments, once.
  • A permissions outage is retried, then the run is parked. It is never reported as "disabled".
Trade-off and what failed
Show what failed and why

An outage used to show up as "disabled in your settings", so users went to check settings that were fine. I split unavailable, misconfigured and disabled into three answers. I also tried LangGraph interrupt(): nested agents without checkpointers never passed the interrupt up, so I kept durable drafts instead.

Case 2 · Prompt-injection defence

A runtime where safety lives in code, not in the prompt

In plain terms: even when a document tries to trick the AI, the code, not the AI, decides what it is allowed to do.

Outcome: A 114-attack suite closed 7 prompt-injection holes. 17/17 parity with the old workflow builder, up from 12/17. Public version: 184 tests, 20 of them attacks.

Problem
Specialist agents take several steps and can change data. A hostile document or a confused model can call the wrong tool, claim the user said yes, save twice or flood the prompt.
My role
Designed and built the agent kit and the side-panel workflow agent on top of it. Both are built and not shipped yet.
Stack
Python, LangGraph, YAML agent cards, SQLite, JMESPath, pytest.
How it works
Show the details
  • Each agent is one folder with a strict card. A write tool that is neither guarded nor confirm-gated makes the card invalid.
  • Risky actions are never run when the model asks. Code stores the exact arguments, writes the question itself, and waits. A fail-closed consent judge reads only that question and the user's reply. Anything but a clear yes cancels.
  • Big tool results go into per-task SQLite. The model queries them with SQL that a deny-by-default authorizer keeps read only.
Trade-off and what failed
Show what failed and why

I tried a Pyodide (WASM) sandbox for the model's queries and rejected it: about 3 s cold start, about 350 MB, and no real isolation. The agent is about 2.6x slower than the old builder and uses 12 to 13x the tokens. The judge is strict, so a polite "yes, thanks" cancels.

Case 3 · Autonomous agent

A planner and executor that run with nobody watching

In plain terms: a user describes a recurring job in one sentence, and the agent plans it and runs it on its own, safely.

Outcome: Planner about 77% cheaper, with 24/24 benchmark and 20/20 end-to-end runs passing after the switch. I analysed 320 QA runs (92% completed) and fed the findings into a hardening list. Public version: 148 tests.

Problem
Users want to say "every Monday, chase overdue tasks in Apollo" and walk away. If the model writes an id or a schedule, one made-up value becomes a real write with nobody there to stop it.
My role
Designed and built the planner and executor end to end, from client discovery to QA handover.
Stack
Python, FastAPI, LangChain structured output, PostgreSQL advisory locks, RRULE, CloudEvents.
How it works
Show the details
  • The goal is grounded against real data first. The model only extracts intent. Code assigns ids, links steps and builds the schedule, and refuses plans that cannot work.
  • Only one worker owns a run, through an atomic claim and a fencing token. A reaper parks runs whose worker died.
  • Hard limits: 90 turns, 150 writes per run, a resume cap and a loop guard. A write ledger turns a repeated write into a no-op, and the final status comes from stored step states, not the agent's words.
Trade-off and what failed
Show what failed and why

The planner was quietly running on the platform's default model, because the service was never registered for model selection. I fixed the routing and moved it to a cheaper model. Each planning call got about 55% slower, which is fine because planning runs in the background.

Case 4 · RAG evaluation

The Three-Hook Model: each check runs where its cost fits

In plain terms: automatic checks that catch it when an AI search-and-answer system starts giving worse answers.

Outcome: A CI gate that cannot switch itself off: an unmeasured threshold or a typo in the threshold file fails. Public version: 165 tests.

Problem
One averaged score hides what went wrong. Retrieval can drift slowly, a judge on every query costs too much, and nothing stops a bad change from merging.
My role
Designed the evaluation framework: four dimensions and three hooks. I planned the production pipeline with two teammates and reviewed the first version. The public repo is my own implementation of the design.
Stack
Python, FastAPI, SQLite, Anthropic and OpenAI judge adapters, GitHub Actions.
How it works
Show the details
  • Hook 1, every query, no LLM: score gap, empty results and p95 latency over a rolling window.
  • Hook 2, a small sample of live traffic, judged in the background: claim-level faithfulness, relevance, context precision and drift.
  • Hook 3, every PR: a golden JSONL set, thresholds and a saved baseline. A metric that gets worse fails CI even above its threshold.
Trade-off and what failed
Show what failed and why

In review I found that the "context" being judged was an intermediate answer, not the retrieved chunks, so the scores compared one answer with another. Hook 2 now checks that every context is a chunk the retriever really returned. A text check alone cannot catch a reworded answer.
