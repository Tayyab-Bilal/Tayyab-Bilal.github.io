Everyone's first answer is a vector database. Mine was grep.

26 Oct 2026 · Agents · Search · RAG

Everyone's first answer to "find the thing the user meant" is a vector database.

Mine was grep.

Picture an AI assistant inside a workspace app. Projects, tasks, emails, docs. A user types "move the Q4 task to next week". Before the agent can do anything it has to know which task.

That search had to respect four things. The data changes every minute. Each user sees different things. People type exact names, senders and ids. And it runs before every reply, so it has to be fast and cheap. A vector index makes all four harder.

A lot of people would reach for Graph RAG here. I didn't. The app's own links already were the graph.

So I split the job in two. Keyword search finds, the model chooses.

Fetch only this user's data, cache it for a few seconds, match phrase first, then words, then fuzzy. That gives a short list. For "the Q4 task" maybe a Q4 report, a Q4 kickoff meeting and the Q4 launch plan. The model reads that list and picks the task. One exact id, and now the agent can act.

If this sounds familiar, it's the classic two stage setup: cheap retrieval, then a smarter reranker. The twist is the reranker is the LLM, and it only ever sees a short list. No index to sync for records, no embedding bill, and a small cheap model is enough.

Finding the right record used to take 1 to 2 minutes. With this it takes about 16 seconds.

The trade-off is real. If the words don't overlap at all keyword can miss, so long documents still get keyword plus vectors.

Two days after I built it, a paper came out pointing the same way: agents searching raw text with plain tools like grep beat embedding retrieval. Link in the comments.

Spend tokens on deciding, not on searching.
