Everyone's first answer is a vector database. Mine was grep.

26 Oct 2026 · 5 min read

  • Agents
  • Search
  • RAG

When an AI assistant needs to find "the thing the user meant", most people reach for a vector database. I used keyword search to build a short list and let the model pick from it.

TL;DR

For records inside a workspace app (tasks, emails, docs, meetings), I match the user's words against that user's own data and hand the model a short list to choose from. There is no index to sync and no embedding bill. Finding the right record went from 1 to 2 minutes to about 16 seconds. The trade-off is real: when the words do not overlap at all, keyword search can miss.

One vague phrase, one exact id

Picture an AI assistant inside a workspace app. Projects, tasks, emails, docs, meetings. A user types "move the Q4 task to next week". Before the agent can do anything, it has to know which task.

Vague words in, one exact record out. That search had to respect four things:

  • FreshTasks and emails change every minute.
  • PrivateEach user sees different things.
  • LiteralPeople type exact names, senders and ids.
  • Every turnIt runs before each reply, so it must be fast and cheap.

A vector index makes all four harder. It is one more copy of the data to keep fresh. Permissions have to be mirrored onto it. Exact names get blurred into "similar" ones. And every record costs an embedding call.

Why not a vector index, and why not Graph RAG

Nested data (workspace, project, task, then docs, emails and meetings) makes a lot of people think of Graph RAG. I did not go that way. The app's own links already were the graph.

A second graph database would have added three things I did not want: sync races with the real data, graph queries written by the model that break, and permissions implemented twice.

The same goes for vectors on records. Workspace data is live, per user and full of literal names, subjects and senders. Those are exact-string problems, and embeddings blur exact strings.

Keyword finds, the model chooses

So I split the job in two. The first part is cheap and exact. The second part needs understanding, so it goes to the model.

The keyword part fetches only this user's data, or reuses a copy cached for a few seconds. Because it only ever searches what that user's own call returned, permissions come for free. It matches the whole phrase first, then the words, then fuzzy. That gives a short list. For "the Q4 task" it might be a Q4 report, a Q4 kickoff meeting and the Q4 launch plan.

The model reads that list and picks the task, because the user said "task". One exact id, and now the agent can act.

Keyword search does the finding. The model does the understanding.

It is not literally grep. It is phrase, word, then fuzzy matching, and the ranking is what makes it work.

find.pysimplified
import difflib

def find(query, records):
    q = query.lower()
    words = q.split()

    def score(r):
        text = r.name.lower()
        phrase = q in text                         # 1. whole phrase
        hits = sum(w in text for w in words)           # 2. how many words
        fuzzy = difflib.SequenceMatcher(None, q, text).ratio()  # 3. fuzzy
        return (phrase, hits, fuzzy)               # compared in this order

    scored = [(score(r), r) for r in records]
    scored.sort(key=lambda s: s[0], reverse=True)
    # keep anything with a phrase, word or fuzzy hit (0.6 is illustrative)
    keep = [r for s, r in scored if s[0] or s[1] or s[2] > 0.6]
    return keep[:10]                                  # a short list

The score is a tuple, so Python compares it left to right. An exact phrase beats any number of word hits, and word hits beat a fuzzy score. That is why a long description full of loose near-matches cannot outrank an exact hit. This sketch is cut down to show the idea, not the real code.

It is retrieve, then rerank

If this sounds familiar, it is the classic two stage setup: cheap retrieval, then a smarter reranker. The twist is that the reranker is the LLM, and it only ever sees a short list.

It is also cheap, for three reasons. There are no embedding calls for records. The model sees snippets, not whole documents. And because it reads a short list, a small cheap model is enough.

Finding the right record used to take 1 to 2 minutes. With this it takes about 16 seconds.

Spend tokens on deciding, not on searching.

Where it breaks, and who else saw this

The trade-off is real. If the words do not overlap at all, keyword search can miss. So for long documents I still use keyword plus vectors, with keyword leading. Vectors earn their place when people paraphrase inside long text. They are a poor fit for finding "the Q4 task".

I am not the only one who ended up here. Two days after I built it, a paper came out pointing the same way: agents searching raw text with plain tools like grep beat embedding retrieval. A second paper reached a similar conclusion later that month. Older work agrees on the keyword side: the BEIR benchmark (2021) found that plain BM25 is a hard baseline to beat out of domain. These point the same way. They do not prove it for your data.

What I'd tell you to do

  • Write down how your users actually name things. If it is literal (names, senders, ids), start with exact matching.
  • Search only what the user's own call returned. Permissions and freshness come with it.
  • Rank with a tuple (phrase, then words, then fuzzy) so an exact hit cannot be drowned out.
  • Keep the list short and let a model choose from it. That is where the understanding belongs.
  • Keep vectors for long documents, where the words may not overlap, and let keyword lead.
  • Time the whole job on your own data. I measured how long it took to find the right record, not how clever the search was.
