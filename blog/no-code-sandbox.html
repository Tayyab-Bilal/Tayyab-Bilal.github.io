I didn't give my agent a code sandbox

2 Nov 2026 · 4 min read

  • Agents
  • Safety
  • SQLite

Everyone building agents is being told the same thing right now: when a tool returns a lot of data, let the model write code to handle it. I measured that. Then I did not do it.

TL;DR

A WebAssembly Python sandbox gave the same results as the alternative, but took about 3 seconds to start and 310 to 390 MB per warm process, and it was not isolated out of the box. I put big tool results in a small in-memory SQLite table instead and gave the model a query tool. SQLite's authorizer makes it read-only. That cost 1.3 MB, queries ran in under a millisecond, and 9 escape attempts did not get through.

The problem is real

An agent calls an API and gets 200 rows back. If you paste them into the prompt, the agent gets slow and expensive, and the model starts making up rows.

So you need a way for the model to work with a big result without reading all of it. The popular answer right now is code.

The popular fix, and what I measured

Anthropic's "Code execution with MCP" and Cloudflare's "Code Mode" both push the same idea. The model writes a small script, a sandbox runs it, and only the answer comes back. It is a good idea, so I measured it.

I tried a WebAssembly Python sandbox. It gave the same results as the alternative. But it took about 3 seconds to start, and it used 310 to 390 MB of memory per warm process.

"Runs in WASM" is not the same as "isolated".

That is the part nobody mentions. Out of the box it was not really a sandbox. It could read every environment variable and call the backend over HTTP. You can lock that down, but then you are building and maintaining the isolation yourself.

What I used instead: boring SQLite

I compared seven options, including SQLite, JMESPath, DuckDB, CEL, jq and a Starlark or Pyodide sandbox. I chose SQLite for the results, plus JMESPath for nested JSON.

The big result goes into a small in-memory SQLite table, one per task. The model does not see the rows. It sees a short summary and a few sample rows, and it gets a query tool. Models are already good at SQL. Most of the time they do not need to run code. They need a smaller language they already speak.

The authorizer does the saying no

SQLite has a feature most people never touch: the authorizer. You give it a function, and SQLite asks that function before every action. Mine says yes to reads and no to everything else.

authorizer.py
ALLOWED = {sqlite3.SQLITE_SELECT,
           sqlite3.SQLITE_READ,
           sqlite3.SQLITE_FUNCTION}

def authorizer(action, *args):
    return (sqlite3.SQLITE_OK
            if action in ALLOWED
            else sqlite3.SQLITE_DENY)

conn.set_authorizer(authorizer)

So a write, a DROP or an ATTACH is refused by the database itself, not by me trying to inspect the query text. Checking text means guessing what a query will do. The authorizer is asked about the actions SQLite is actually about to take.

The rest of the guard rails are plain: one statement per query, a half-second timeout, and output capped at 200 rows.

The model writes the query. The database decides what it's allowed to touch.

These are my measurements on my setup. Nine attempts is a test, not a proof. SQL covers filtering, grouping and counting. If your agent has to run arbitrary code over the data, you need something heavier than this.

What I'd tell you to do

  • Measure the sandbox on your own setup: cold start, memory per process, and what it can reach (environment variables, the network).
  • Do not treat "runs in WASM" as isolation. Test what it can read and call before you trust it.
  • Give the model a smaller language it already knows, such as SQL, before you give it a general one.
  • Enforce the rules in the database (the authorizer), not by inspecting query text.
  • Add limits as well: one statement, a timeout, a row cap.
  • Write the escape attempts down and keep running them.
  • When someone asks for a big thing, bring a cost table, not just a yes or a no.
