I didn't give my agent a code sandbox

2 Nov 2026 · Agents · Safety · SQLite

Everyone building agents is being told the same thing right now. When a tool returns a lot of data, let the model write code to handle it.

I measured it. Then I didn't do it.

The problem is real. An agent calls an API and gets 200 rows back. Paste them into the prompt and it gets slow, expensive, and the model starts making up rows.

The popular fix is a code sandbox. The model writes a small script, the sandbox runs it, only the answer comes back.

So I tried a WebAssembly Python sandbox. Same results. But about 3 seconds to start and around 350 MB of memory per process.

And the part nobody mentions. It wasn't really a sandbox. Out of the box it could read every environment variable and call the backend over HTTP. "Runs in WASM" is not the same as "isolated".

What I used instead is boring. The big result goes into a small in memory SQLite table, and the model gets a query tool.

SQLite has a feature most people never touch, the authorizer. You give it a function and it checks with that function before every action. Mine says no to everything except reads. So a write, a DROP or an ATTACH is refused by the database itself, not by me trying to inspect the query text.

1.3 MB of extra memory. Queries in under a millisecond. I threw 9 escape attempts at it and none got through.

Models are already good at SQL. Most of the time they don't need to run code. They need a smaller language they already speak.

The model writes the query. The database decides what it's allowed to touch.
